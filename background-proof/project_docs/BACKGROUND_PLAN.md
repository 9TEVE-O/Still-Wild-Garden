## Background writer

Reopen this linked Site with Sites `get_site`. Verify owner-private access and active publication; obtain its current service credential from that response. Send the credential only to this exact Site in `OAI-Sites-Authorization: Bearer ...`. It is consumed by Sites dispatch. Collect the exact Open-Meteo URL in lib/weather.ts from the cloud-task runtime (Darwin, UTC Unix timestamps, stated units, three past days and two forecast days). POST `/api/background/tick`, content type `application/json`, body `{"trigger":"schedule","scheduler":{"taskId":"<scheduler task ID>","executionId":"<independent receipt execution ID>","triggeredAt":<receipt time, epoch ms>},"weather":<unmodified provider JSON>}`. A scheduled delivery must carry `scheduler` with exactly those three fields (non-empty IDs of at most 200 characters; a positive integer time). A scheduled delivery without it, with extra fields in it, or scheduler metadata on a `manual` trigger is rejected with HTTP 400 and changes nothing. An execution ID binds to one garden run only; a reused ID is refused and creates no run. The bounded inputs are a caller-declared trigger label, that correlation metadata and a validated provider response, limited to 65,536 characters and 200 hourly samples. Record the fetch status; do not fabricate a weather response. If collection fails, send the same body without `weather` so the server attempts its own fetch and applies its documented fallback. It cannot choose a garden, seed, timestamp, weather or mutation. HTTP failures and uncommitted progress are not a success. Each call validates the scheduler-relayed feed (or collects from the hosted Worker), saves selected completed UTC-hour environmental samples, and processes at most 24 oldest due intervals (`MAX_CATCH_UP` in lib/world.ts), so a longer backlog drains over successive runs. It can execute with no viewing browser.

GET `/api/evidence` with the same service access. Read back the returned run ID, committed-tick count, revision, last UTC tick and events; report errors and remaining backlog. This read does not advance or log a viewing visit. Never navigate to `/`, call `/api/snapshot`, use the old public origin garden or rebuild the Site as part of a routine run.

## Simulation and consistency

Each tick is the preceding hour ending on an aligned UTC boundary. Rain is applied once. Provider values, units, valid interval, retrieval time and fetch revision are retained; each committed tick pins one input. New model revisions do not rewrite earlier outcomes. Future inputs are excluded. Non-rain weather values are instantaneous at interval end; rainfall covers the preceding interval.

Pip cycles finding space, sowing and resting. Sowing adds one stored plant when habitat exists. Dew cycles spring collection, carrying and watering roots. Watering changes stored soil moisture. Moss cycles observation, making space and rest. Making space adds one habitat slot. Counts change through saved transitions, never through elapsed-time reconstruction in the viewing code. Local movement remains animation and does not establish intelligence or a saved task's position. There are no external keeper actions.

Model inputs influence rain accumulation, daylight-related moisture use and the shown atmosphere. Missing intervals use zero-rain, explicitly simulated creative conditions, never rain from another hour. Exact archived intervals older than six hours are labelled stale. Plants never die from absence. These rules are creative world units and are not scientifically calibrated.

D1 atomic batches guard the prior revision/last-tick position, insert a unique garden/rules/tick key, insert stable consequence IDs and update the world. A stale concurrent computation commits nothing; SQL failure rolls the batch back. The background run succeeds only after commits. A worker crash may leave a `running` attempt, so audit applied ticks for its committed progress instead of assuming it never acted. Scheduler trigger labels are caller declarations; correlate run IDs with independent scheduler/Worker logs to establish provenance.

## Read path and proof

GET `/api/snapshot` and GET `/api/evidence` only read state, events, runs and proof records in one read-only database batch; neither writes to D1, advances the world or fetches weather. The snapshot route serves garden data only to a view session that the same read shows open in D1, named in the `X-Stillwild-View-Session` header: a missing or malformed header returns HTTP 400, and an unknown or closed session HTTP 409, with no garden data and no write. A served read emits a `stillwild_snapshot_view` Worker log and a refused one `stillwild_snapshot_refused`. Service and review reads use GET `/api/evidence`. The page records every view in D1 through POST `/api/view/session` (`{"sessionId":"<uuid>","event":"open|read|heartbeat|close"}`) before it reads: `open` when a view starts, `read` before each snapshot request, `heartbeat` every 30 seconds and `close` on page hide or unmount. Reads and heartbeats are recorded even when their session is already closed, and a read proceeds only on an open session. If a view cannot be recorded, the page does not read the garden. The browser reads on opening, reconnecting, becoming visible and every five minutes while visible. The canvas uses stored plant counts; frequent redraw is local movement. SSE is deferred.

The first authenticated writer saves an immutable creation baseline and never replays pre-birth hours. After final publication and access verification, POST `/api/proof/start` with exactly `{"allViewsClosedAttested":true}` (the owner's attestation that every garden view is closed) through the same private service boundary; any other body is rejected with HTTP 400. This records a separate immutable absence-check baseline without changing world state. Retries preserve its original start time. Publish-triggered platform captures can open the view, so start this proof checkpoint after all publishing finishes. Close every test-garden view for at least 24 hours. After baseline+24 hours, inspect background data before the first viewing read; corroborate saved tick commits and meaningful keeper events with independent scheduler and Worker logs. Review `stillwild_snapshot_view` logs for visits during the window. Absence is a human/independent-log assertion and is not inferred from a database timestamp. The API conservatively reports proof pending until a separate review establishes it. Do not promote that state automatically after time elapses.

View-closure gate. The original checkpoint `absence-check-001` stays immutable and its executed review INCONCLUSIVE; the snapshot and evidence report it on its own as `proof.originalCheckpoint`, while `proof.baseline`, `proof.earliestCheckAt` and `proof.viewCoverage` belong to the second-window checkpoint `absence-check-002`. Starting that checkpoint is refused with HTTP 409 while any view session lacks a recorded close, however old its last heartbeat, because a suspended tab sends no heartbeat. GET `/api/evidence` lists such sessions under `proof.unclosedViewSessions`. Close one only after confirming its tab is gone, with POST `/api/view/session` `{"sessionId":"<id>","event":"close"}`; that close is itself recorded. Attest only once `proof.unclosedViewSessions.count` reads 0. The check, the checkpoint row and its gate row commit in one D1 batch, and the gate stores the unclosed-session count measured inside it. Inside the 24 hours, any recorded open, read, heartbeat or close, or any session open at or after the start or last seen inside the window, makes `allViewsClosedConfirmed` false.

This plan describes the source in this repository. CURRENT_BUILD_STATE.md records which source revision the private Site runs; a GitHub commit does not deploy it.

A successful initial write/read proves writer accessibility, not a scheduled run or 24-hour operation. TypeScript/build/SQLite tests have their own narrower scope. Separate-user ownership and cloud/mobile synchronisation are deferred until the isolated proof passes.

## Hosted weather transport check, 4 October 2026

The initial hosted Worker fetch received Open-Meteo HTTP 429. A cloud-task-runtime probe of the identical URL returned HTTP 200 with 120 hourly rows, UTC offset 0 and the required units. The supported job therefore collects once in that runtime and relays the unmodified provider JSON through the protected writer; source transport is recorded on every sample. This is a rate-limit handling change, not a second provider or a scientific claim. Cloud deployment and write/read for the relay still need their own evidence.

For relayed samples, `fetchedAt` is the garden server's receipt time. The scheduled job must retain the actual provider HTTP status and fetch time in its run output. UTC valid interval identity still determines rain accounting, independently of either retrieval timestamp.
